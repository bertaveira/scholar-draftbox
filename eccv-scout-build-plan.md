# ECCV Scout — Build Plan

## 1. Goal

Build and publicly launch **ECCV Scout**, an unofficial, free web app that helps ECCV attendees:

- discover relevant papers from the full conference program
- search papers semantically using natural language
- get personalized recommendations
- save papers they care about
- see saved papers grouped by session / day / poster location
- build a lightweight personal conference schedule
- use the site easily from a phone while at the venue

The app should be:

- **free to host**
- **publicly accessible**
- **open source**
- **fast on mobile**
- **usable without creating an account**
- **robust even if AI/search services temporarily fail**
- realistic to build and launch quickly

# 3. MVP Scope

The MVP should solve one core problem:

> There are too many ECCV papers to browse manually. Help me find the ones I care about and turn them into a practical conference plan.

## Must-have features

### A. Explore papers

Each paper card should show:

- title
- authors
- abstract or short summary if available
- ECCV topic / track labels
- session
- date and time
- room
- poster number
- paper / project link when available
- save / star button

Filters:

- topic
- day
- session
- oral / poster if available
- saved only

Search:

- normal text search across title, authors, abstract, and keywords

---

### B. Semantic search

Allow queries like:

- "world models for robotics"
- "fast video diffusion"
- "3D reconstruction using generative priors"
- "vision-language models for embodied agents"

Flow:

1. user enters a natural-language query
2. frontend sends only the query text to `/api/embed`
3. Cloudflare Workers AI returns an embedding
4. browser compares that vector against precomputed paper embeddings
5. browser ranks and displays the most relevant papers

No database should be required.

---

### C. Personal recommendations

On first use, ask:

> What are you interested in at ECCV?

The user can enter a few topics or a short paragraph.

Generate an embedding for that interest description.

Then rank papers using:

- similarity to stated interests
- similarity to starred papers
- optional negative signal from hidden / disliked papers
- diversity bonus so results are not all near-duplicates

A simple first formula is sufficient:

```text
score =
    0.55 × stated_interest_similarity
  + 0.35 × starred_paper_similarity
  - 0.10 × rejected_paper_similarity
```

This can be refined later.

---

### D. Save papers

Every paper should have a clear:

- ☆ Save
- ★ Saved

button.

Saved papers are stored locally in the browser.

No login.

Use:

- `localStorage` for simplest implementation
- or IndexedDB if the stored dataset becomes too large

---

### E. My ECCV

Create a personal schedule view.

Group saved papers by:

1. day
2. session
3. room / poster location

Example:

```text
Thursday

Poster Session 2 — 14:00–16:00

#135  Paper A
#222  Paper B
#287  Paper C
```

The app should flag obvious schedule conflicts.

---

### F. Poster-session mode

This is potentially the most useful conference-day feature.

When a session is active, show only saved/recommended papers in that session:

```text
Poster Session 4

★★★★★  #222 — Paper title
★★★★☆  #135 — Paper title
★★★★☆  #287 — Paper title
```

Sort primarily by recommendation score.

This makes ECCV Scout useful while physically walking through the poster hall.

---

# 4. Features to Explicitly Avoid Before Launch

Do **not** build these initially:

- user accounts
- email login
- social features
- comments
- PDF hosting
- citation-manager integration
- chat assistant
- complicated LLM summaries
- recommendation explanations generated by an LLM
- collaborative schedules
- mobile apps
- admin dashboard
- database-backed user profiles

These are distractions until the core paper discovery experience works.

# 8. Data Ingestion Plan

## Step 1 — Fetch ECCV paper list

Build:

```text
scripts/scrape_eccv.py
```

It should extract:

- title
- authors
- topic labels
- paper type
- session
- date
- time
- room
- poster number
- official link

Output:

```text
data/papers.raw.json
```

---

## Step 2 — Normalize data

Build:

```text
scripts/normalize_papers.py
```

Responsibilities:

- normalize whitespace
- normalize author names
- convert times to a consistent format
- convert dates to ISO format
- create stable IDs
- remove duplicates
- validate required fields

Output:

```text
data/papers.json
```

---

## Step 3 — Enrich abstracts

Try to obtain abstracts from reliable public sources.

Priority:

1. official ECCV source
2. linked official paper page
3. OpenReview if applicable
4. project page

Do not block launch if some abstracts are missing.

For papers without abstracts, embeddings can use:

```text
title + topics + authors
```

---

## Step 4 — Generate embeddings

For each paper create an embedding from:

```text
Title: ...
Topics: ...
Abstract: ...
```

Store embeddings separately from metadata.

Suggested format:

```text
data/paper_embeddings.bin
data/paper_embedding_index.json
```

The index maps:

```json
{
  "eccv-2026-1234": 0,
  "eccv-2026-1235": 1
}
```

to vector positions.

This avoids making the main `papers.json` unnecessarily huge.

# 10. Search Architecture

## Keyword search

Run entirely in browser.

Search across:

- title
- authors
- topics
- abstract

A simple fuzzy-search library is enough.

Possible option:

```text
Fuse.js
```

---

## Semantic search

Endpoint:

```text
POST /api/embed
```

Input:

```json
{
  "text": "vision language models for robots"
}
```

Output:

```json
{
  "embedding": [0.123, -0.234, ...]
}
```

The frontend then calculates cosine similarity locally.

Pseudo-code:

```ts
for (const paper of papers) {
  paper.score = cosineSimilarity(
    queryEmbedding,
    paperEmbedding
  );
}
```

Sort descending.

# 11. Recommendation System

Start simple.

## User profile

Store:

```ts
type UserProfile = {
  interests: string;
  interestEmbedding?: number[];
  starredPaperIds: string[];
  hiddenPaperIds: string[];
};
```

Create:

```text
interest vector
      +
mean(starred paper vectors)
      -
mean(hidden paper vectors)
```

Then compare that profile vector against all papers.

---

## Diversity

Without diversity, recommendations may contain ten nearly identical papers.

After ranking, apply a simple diversity step.

For example:

1. take highest scoring paper
2. downweight candidates extremely similar to already-selected results
3. repeat

This can be added after the first version works.

# 17. Automatic Data Refresh

Conference programs may change.

Create GitHub Action:

```text
.github/workflows/update-data.yml
```

Run periodically during the conference period.

Workflow:

```text
fetch ECCV data
       ↓
normalize
       ↓
compare with current dataset
       ↓
if changed
       ↓
validate
       ↓
commit updated data
       ↓
redeploy
```

Important:

Do not automatically publish malformed data.

Run validation before committing.

Checks should include:

- paper count did not suddenly drop dramatically
- titles are present
- sessions are recognized
- no duplicate IDs
- dates parse correctly

# 18. Failure Modes

The application should degrade gracefully.

## If Workers AI fails

Still allow:

- browsing
- keyword search
- filtering
- saved papers
- schedule
- session mode

Display:

```text
Semantic search is temporarily unavailable.
You can still search by title, author, or topic.
```

---

## If ECCV source changes

Keep the latest valid dataset live.

Do not replace it with a broken scrape.

---

## If abstract enrichment fails

Use:

```text
title + topics
```

for ranking.

The paper should remain visible.

---

# 19. Privacy

Keep privacy extremely simple.

Suggested copy:

> Your research interests, saved papers, and personal schedule are stored in your browser and are not uploaded to ECCV Scout. Semantic search queries are sent to our embedding endpoint only to calculate search vectors.

Do not add third-party tracking before launch unless there is a compelling reason.

---

# 20. Performance Targets

Aim for:

- initial page usable quickly on conference Wi-Fi
- no huge JavaScript bundle
- lazy-load abstracts if necessary
- cache paper metadata aggressively
- avoid downloading PDFs
- keep embeddings compact
- perform ranking in a Web Worker if UI blocking becomes noticeable

Suggested vector format:

```text
Float16 or Float32 binary
```

instead of massive JSON arrays if needed.

---

# 21. Mobile UX Priorities

Design for someone standing in a poster hall with one hand holding a phone.

Buttons must be:

- large
- obvious
- easy to tap

Poster-session screen should prioritize:

1. poster number
2. paper title
3. recommendation score
4. saved status
5. location

Avoid dense desktop-style tables on mobile.

# 25. Definition of MVP Success

The MVP is successful if an ECCV attendee can:

1. open the site on their phone
2. describe what they work on
3. immediately see relevant ECCV papers
4. search for a research topic naturally
5. save interesting papers
6. open a session and see which posters they should visit
7. view all saved papers as a personal ECCV plan

That is enough.

Everything else can wait.
